#+title: Present, export and publish

* Publication verification

Plugin 0.15 records successful workspace pushes in private local state under
=~/.local/state/matsugit/publications/= (or =XDG_STATE_HOME=). These receipts
contain revisions, URLs and a source hash, never document text or credentials.
The publication status button distinguishes saved local text from a pushed
revision and a provider-verified deployment. Network checks happen only when
requested; missing CLI authentication leaves deployment unverified.

For GitHub, verification uses the latest =github-pages= deployment/status, or
the latest branch-based Pages build, and requires the exact pushed SHA.
A passing Actions workflow alone is not publication.

For GitLab, the pipeline SHA and branch are checked, but a green pipeline is
not proof of deployment. GitLab's Pages metadata has no commit SHA. If your
existing pipeline records a deployment environment, set
=deployment_environment= to its exact name in the named target's JSON settings.
Only a successful latest deployment for that environment with the matching SHA
is labelled =Published=. Without that evidence the UI honestly says =Pushed=.
No CI/Pages settings are changed automatically, and older manually configured
pipelines continue to work as before.

Provider contracts: [[https://docs.gitlab.com/api/pages/][GitLab Pages]],
[[https://docs.gitlab.com/api/deployments/][GitLab deployments]],
[[https://docs.github.com/en/rest/deployments/statuses][GitHub deployment statuses]].

* Present now
In the Codex or Cursor workspace, select Document or Slides, then click the
presentation-screen icon. The selected format stays selected. Slide arrows/Space
advance; document mode keeps its reading layout with page scrolling. Escape returns
to your previous editor layout. If the host blocks native fullscreen, the workspace
still becomes a content-only presentation. This does not
save, publish or require hosting.

* Downloads and local synced folders
The download icon opens an export picker:

| Format | What it preserves |
|--------+-------------------|
| Source | The current Markdown or Org draft |
| HTML | Self-contained rendered slides; use ZIP for working document/source links |
| ZIP | Reading document, slides, editable source and supporting files |
| PDF | Rendered slide styling, without editable slide objects |
| PowerPoint | Editable text and native tables; charts/diagrams as images |

PowerPoint is an editable adaptation, not a CSS-to-PowerPoint clone. The selected
theme's chart palette colors the generated native template. Complex compositions,
merged cells, fonts and sizing can differ. Review before sharing. For a closer
corporate match, provide a native PowerPoint reference template:
#+begin_src sh
matsugit export deck.md --format pptx --output deck.pptx --reference-doc template.pptx
#+end_src
A trusted theme pack can set ="powerpoint": "template.pptx"= in =theme.json=.
The referenced file is copied like other manifest-listed theme assets. With no
template, the generated default is widescreen 16:9. Native text and tables stay
editable; this does not promise native editable Mermaid or Vega-Lite shapes.

For PDF or Mermaid-to-PowerPoint capture, install the isolated browser once:
#+begin_src sh
matsugit setup-export
#+end_src
No browser is installed implicitly. Capture blocks network requests; render
accepts only the existing local asset rules, and never executes document code.

CLI examples:
#+begin_src sh
matsugit export deck.md --format zip --output deck.zip
matsugit export deck.org --format pdf --output deck.pdf
matsugit export deck.md --format html --output deck.html
#+end_src
Ordinary exports refuse an existing output unless =--replace= is explicit.
Synced exports reuse their stable filename as described below. The plugin exports the current
draft without saving over the source; CLI exports the source on disk. ZIP includes
editable source, and slide HTML can include speaker notes: hidden is not private.

** OneDrive without an API
Choose an existing local folder already managed by OneDrive (or another sync app):
#+begin_src sh
matsugit export-folder "$HOME/Library/CloudStorage/OneDrive-Example/Decks"
matsugit export deck.md --format pptx --sync-folder
#+end_src
Use the actual folder on your machine, not the example above. No account is
connected, no permissions change, and no cloud API is used. Once configured,
=Synced folder= appears in the workspace export dialog. Repeated exports update
the same =deck.pptx= (or other chosen format). Private local receipts identify
unchanged matsugit exports; a file edited externally, created elsewhere or owned
by a different source requires explicit =--replace= or the dialog's replacement
checkbox. Check with collaborators before discarding their PowerPoint edits.
Existing dated copies are not deleted. Stable names do not guarantee OneDrive
version history or successful upload: check the sync app. Source download remains
a browser download. Updating a source does not export automatically; select Export.

* Configurable Git targets
In the workspace, click the upload icon and the =+= beside Target to connect an
online repository. Choose GitHub/GitLab and its hostname, then list repositories
using the existing =gh=/=glab= login. The list is paginated; an exact
=owner/repository= or =group/subgroup/project= also works. =Connect checkout=
clones into a private local matsugit directory or selects an already configured
target. It does not push, change the default, create a repository, enable Pages,
modify CI or grant account access. Existing Git authentication must also work.
Then review =Source to CI= and explicitly commit/push. An unprepared repository
will ask for CI setup rather than silently installing a deployment pipeline.

Register an existing clean checkout; this does not clone or publish:
#+begin_src sh
matsugit target set docs --repo /path/to/docs --provider gitlab --default
matsugit target set github-docs --repo /path/to/github-docs --provider github
matsugit target list
matsugit publish-plan deck.md --target docs
#+end_src
Optional settings include =--branch=, =--remote=, =--site-dir=, =--site-url=,
=--theme= and =--expected-remote=. The last requires an exact credential-free Git
remote match. The default branch is =main= and the remote is =origin=.

In Codex, click the upload icon, choose a target, and select =Review target=.
The source must be saved first. Inspect the repository, branch, output directory
and theme, then explicitly select =Commit and push=. Source or checkout changes
invalidate the plan. Unknown files are not overwritten, dirty target checkouts
are refused, and unrelated unpublished commits are not pushed. A push may trigger
the target's existing CI even when the additional CI checkbox is off.

The default target applies to publication only, not ordinary previews or downloads.
A source project's =matsugit.json= may set =publish_target=; an explicit project
=repo= retains its old behavior and takes precedence over the global default.
=--target= selects a named target explicitly. Current-repository publication remains
the fallback when no target is configured.

#+begin_src sh
matsugit publish deck.md --target docs
#+end_src
The CLI asks before committing/pushing. =--yes= supplies explicit confirmation;
=--deploy= additionally requests an already-installed deployment workflow. Do not
use either merely to preview a document. Hosting availability and access control
must be checked separately: pushing is not proof that Pages is live or private.

** Existing CI stays intact
No deployment workflow or hosting setting changes when configuring a target.
For a new site, =matsugit setup-ci --provider github --repo /path/to/docs= (or
=gitlab=) writes opt-in CI files and refuses to overwrite existing ones. Review
them before committing. GitLab requires explicitly including its generated file;
hosting and authentication remain the operator's responsibility.

For an existing static-site pipeline, point =--site-dir= at a directory it already
copies. The pushed bundle contains both outputs and source. Such a copy-only path
does not automatically rebuild after editing the bundled source: republish through
matsugit, or use the explicit matsugit CI rebuild integration. Private deployment
wrappers remain separate; the Codex publisher refuses =deployment: tailscale=
and directs you to the existing private CLI/Emacs command.

** Source to CI: build on the server
Select =Source to CI= in the upload dialog, or configure a target once:
#+begin_src sh
matsugit target set docs --repo /path/to/docs --provider gitlab --build ci
matsugit publish-plan deck.md --target docs
matsugit publish deck.md --target docs --deploy
#+end_src
This commits normalized, editable Markdown/Org, referenced assets and trusted
theme files. It does not build HTML/slides locally. Pandoc prepares the inert
source bundle; CI runs Quarto and produces both versions. Org remains Org.
Use =matsugit setup-editor= if the local Pandoc converter is unavailable.

For a new target first install and review =setup-ci= as above, commit its files,
and configure the hosting permissions yourself. The generated GitHub workflow
is manual; GitLab accepts web/API pipelines. A plain push does not override those
rules: use =--deploy= or the existing CI UI when appropriate. Older CI installations
without source-bundle support are refused; their files are not silently replaced.

An existing =scripts/build_pages.py= pipeline scanning =topics=, =guides=,
=presentations= and =exports= can use the =topics= adapter:
#+begin_src sh
matsugit target set docs --build ci --ci-layout topics --source-dir topics/matsugit
#+end_src
This adapter sends only source/assets; the target's existing renderer controls
the theme and output routes. It does not copy the local preview theme or alter CI.
Editing a published bundle in Git is supported by CI. Publishing a separate local
copy refuses remotely edited source/assets until you reconcile them. Review the
plan every time; a source-only push is still publication, not a preview.
